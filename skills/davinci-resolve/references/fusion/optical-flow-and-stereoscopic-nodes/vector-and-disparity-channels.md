### Vector and Disparity Channels


Forward and reverse optical flow are held in the Vector and BackVector channels respectively. A more apt label for the Vector channel would be “forward vector” or “forward flow,” because calling a channel “Vector” is “not technically correct” — as a more mathematically-inclined user may note, every channel apart from the scalar channels Z/ID counts as a “vector” channel in the technical sense. A frame’s Vector aux channel records the flow running forward from the present frame into the following frame of the sequence, while its BackVector aux channel records the flow running backward from the present frame into the preceding one. Should the prior or following frame be absent (whether missing from disk, or because a Loader’s global range keeps OpticalFlow from reaching it), Fusion populates the matching channels with zeros (transparent black). Within the Disparity channel sit the displacement vectors that pair each pixel in one eye with its counterpart in the other eye. Vectors that map left > right live in the left image’s Disparity channel, and vectors that map right > left live in the right image’s Disparity channel. As an illustration: `(xleft, yleft) + (Dleft. x, Dleft. y) -> (xright, yright)` `(xright, yright) + (Dright. x, Dright. y) -> (xleft, yleft)` For pixels that aren’t occluded you’d anticipate that Dleft = -Dright, though the disparity generation algorithm makes that equality only approximate. Keep in mind that Disparity records both X and Y figures, since left/right images are seldom registered exactly in Y, even when shot with a carefully set up camera rig. Both Disparity and Optical Flow figures are kept as un-normalized pixel shifts. Notably, this departs from Fusion’s resolution-independent convention. The convention was settled on after long deliberation, so that a user need not fret over rescaling the Disparity/Flow figures when an image is cropped, nor over computing scale factors when these channels are imported into or exported from other applications. Since the Flow and Disparity channels record their data as pixel shifts, that can introduce trouble with Proxy and AutoProxy. Here Fusion’s rule is that, for proxied images, those channels keep unscaled pixel shifts that hold for the full-sized image. Therefore, to reach the disparity values from a script or through a probe, always recall that you must scale them by (image. Width/image. OriginalWidth, image. Height/image. OriginalHeight). And when you work with Vector and BackVector aux channels, bear in mind that every node assumes these aux channels carry the flow spanning consecutive frames.

To put it more exactly, given a run of three frames A, B, C, then: B Vector will hold the flow B>C B BackVector will hold the flow B>A A Vector will hold the flow A>B A BackVector is filled with zeros since no frame precedes A C Vector is filled with zeros since there is no frame D for a C>D flow C BackVector will hold the flow C>B As you handle these channels, the burden falls on the user to honor these rules (or, for ingenious users, to set them aside). A node such as TimeStretcher won’t behave properly, because it still presumes the channels carry flow offset forward/back by 1 frame. NOTE: At present, DoD/RoI has yet to be supported across every one of the Fusion nodes.
